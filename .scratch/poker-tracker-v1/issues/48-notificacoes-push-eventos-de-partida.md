Pedido do Organizador: estender pra três novos eventos — partida começou, jogador saiu, partida terminou — e, junto, garantir que **toda** notificação do app (as que já existem e as novas) siga o mesmo padrão push+in-app, não só a de blind.

**Blocked by:** 54 (o interruptor global de notificação mora na tela de Configurações) — a infraestrutura de push em si (VAPID, service worker, `useNotificacoesDoTimer`/`BotaoNotificacao`) já existe e é reaproveitada aqui.

**Status:** done

## Dois níveis de inscrição, não só um

Discutido com o Organizador: além do botão contextual que já existe (ativar notificação *desta* Partida, na tela do Timer), o pedido é também um **interruptor global** em Configurações (ticket 54) — "quero saber sempre que rolar uma Partida, sem precisar já estar com a tela dela aberta". Os dois convivem.

- [x] `push_subscriptions.partida_id` passa a aceitar `NULL` (migration `1786543705302_inscricao-global-de-notificacao`) — `NULL` = inscrição **global** (recebe partida começou / partida terminou / jogador saiu de **qualquer** Partida); preenchido = inscrição **contextual** de hoje (troca de nível de blind, só daquela Partida). Índice único parcial novo (`push_subscriptions_endpoint_global_unica`, só `endpoint`, só `WHERE partida_id IS NULL`) — a constraint `(partida_id, endpoint)` original não pega duplicata nas linhas globais (SQL trata cada `NULL` como distinto)
- [x] Novo endpoint `POST/DELETE /api/notificacoes/inscricao` (sem id de Partida na URL) — `src/app/api/notificacoes/inscricao/route.ts`, reaproveitando `salvarInscricao`/`removerInscricao`/`ehAssinaturaValida` de `src/lib/push.ts` com `partidaId = null`; é o que `ToggleNotificacaoGlobal` (ticket 54) chama
- [x] Hook do cliente generalizado e movido pra `src/hooks/use-notificacoes-push.ts` (era `src/app/partidas/[id]/use-notificacoes-do-timer.ts`, usado só ali) — `useNotificacoesPush(partidaId: number | null)`, reaproveitado tanto por `BotaoNotificacao` (contextual) quanto por `ToggleNotificacaoGlobal` (global, `null`). Importante: `desativar()` **não** chama mais `assinatura.unsubscribe()` no navegador — só apaga a linha do nível desativado no servidor, porque agora o mesmo `endpoint` do navegador pode estar servindo os dois níveis ao mesmo tempo (desligar um não pode matar o outro)
- [x] Novas funções em `src/lib/push.ts`, no mesmo padrão de `notificarMudancaDeNivel` (`Promise.allSettled`, nunca lança): `notificarPartidaComecou`, `notificarJogadorSaiu`, `notificarPartidaTerminou` — todas buscando via `buscarInscricoesDaPartida` (`WHERE partida_id = $1 OR partida_id IS NULL`, com `DISTINCT ON (endpoint)` pra dedupe). Limpeza de inscrição inválida (404/410) também generalizada: `removerInscricoesInvalidas(endpoint)` apaga **todas** as linhas daquele endpoint (contextual e global), não só a que falhou — um endpoint revogado pelo navegador está inválido nos dois níveis
  - `notificarPartidaComecou(partidaId)` — chamada a partir de `iniciarTimer` (`src/lib/timer.ts`), só no **primeiro** "Iniciar" de verdade da Partida (checado via `SELECT 1 FROM timers_de_partida` antes do upsert, dentro da mesma transação) — não dispara de novo a cada retomada depois de uma pausa
  - `notificarJogadorSaiu(partidaId, nome, posicao)` — chamada a partir de `marcarSaida` (`src/lib/partidas.ts`), depois de recarregar a Partida (nome/posição vêm de lá — `travarPartidaEditavel` não traz nome, só a trava)
  - `notificarPartidaTerminou(partidaId, classificacaoFinal)` — chamada a partir de `finalizarPartida` (`src/lib/partidas.ts`), com o top 3 da classificação final (`formatarTop3Texto`, função pura extraída pra ser testável sem mock de banco)
- [x] `notificarMudancaDeNivel` (blind, ticket 39) **continua só contextual** (`WHERE partida_id = $1`, sem `OR NULL`) — não alterada
- [x] O Timer é encerrado junto da Partida — **mas na rota, não dentro de `finalizarPartida`**: `finalizarPartida` (`src/lib/partidas.ts`) chamar `encerrarTimer` (`src/lib/timer.ts`) diretamente criaria um import circular (`timer.ts` já importa `buscarPartidaPorId` de `partidas.ts`). Resolvido em `POST /api/partidas/[id]/finalizar/route.ts`: chama `finalizarPartida` e, com o resultado em mãos, chama `encerrarTimer` (best-effort, `try/catch` — uma falha aqui não desfaz a Partida já finalizada)
- [x] Levantadas as notificações que já existem hoje (toasts/banners de erro, o beep do ticket 37): nenhuma delas faz sentido virar push — são feedback imediato de uma ação que a própria pessoa acabou de fazer com o app aberto (ex: "Salvo!", erro de validação), diferente de blind/começou/saiu/terminou, que fazem sentido chegar com o app fechado. Nenhuma mudança nelas.
- [x] Payload de cada evento novo no mesmo formato (`titulo`/`corpo`/`url`) de `notificarMudancaDeNivel`
- [x] Testes: `formatarTop3Texto` (unitário, `src/lib/push.test.ts`, 4 casos — ordenação, sem posição ainda, menos de 3, vazio). O dedupe em si (`DISTINCT ON`) **não** ganhou um teste dedicado com mock de banco — validado só indiretamente (91/91 testes de integração passando com as chamadas novas dentro de `iniciarTimer`/`marcarSaida`/`finalizarPartida`, que rodam sem VAPID configurado no ambiente de teste e portanto viram no-op — ver `garantirConfigurado`)

**Nota sobre o pedido original de "timer vivo na notificação":** investigado e descartado — cronômetro contando dentro da notificação do sistema (estilo Live Activity do iOS ou notificação com chronometer do Android) exige app nativo, não é possível via Web Push/PWA. O que este ticket cobre são notificações pontuais nos eventos, que é o que dá pra fazer nesta arquitetura.
